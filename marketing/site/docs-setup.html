Set up a connection

Everything between tapping ＋ and having a live shell: the fields, the key, the fingerprint prompt, the multiplexer choice, and what Moshpit does when the host turns out not to have tmux, herdr or mosh-server. About a minute if the host is ready.

Add the host

Name, Host, Port, Username. Save turns on the moment Name and Host both have text — everything else has a working default.

Pick how you sign in

A password, a key you generate on the phone, or a PEM you paste. The secret goes to the iOS Keychain; the connection record only holds a reference to it.

Check the fingerprint

The first handshake stops and shows the host key with the ssh-keygen line to compare it against. Trust, or Cancel.

Step 1

Add the host

Home has two round buttons in its header: the gear for Settings and ＋ for a new connection. ＋ opens Add Connection; the same form is the editor — long-press a card, choose Edit, and it opens as Edit Connection.

CONNECTION

Four fields, two of them required

Name is what you see on the card. Host is a hostname or an IP. Port defaults to 22 and is used for both SSH and the mosh bootstrap — there is one port field, not two.

  • Save is enabled as soon as Name and Host are non-empty
  • Username is not checked — leave it blank and the form still saves, so fill it in
  • Everything under ROAMING · MOSH and ADVANCED is optional

Where the details are kept

Connection metadata — name, host, port, username, your multiplexer choice — is a JSON array in UserDefaults. The password or private key is not in there. It goes to the iOS Keychain as a generic password item, and the connection only stores an opaque reference like moshpit.secret.<uuid>.

Keychain items are written with kSecAttrAccessibleWhenUnlockedThisDeviceOnly: readable only while the phone is unlocked, and excluded from backups and from device transfer. That is deliberate, and it has a cost — see a new phone starts over below.

Deleting one

Long-press a card for Open or Connect, Edit, Disconnect (when it is live) and Delete Connection. The confirmation says exactly what it does: Removes the saved server and its stored credentials from this device. If the connection points at a key from the SSH Keys screen, that key is left alone — only a secret owned by this connection is dropped.

What delete does not do: it does not forget the host fingerprint you trusted. That entry stays in the Keychain, keyed by host and port.

Hosts on your LAN

The first time Moshpit reaches a local address, iOS asks for Local Network permission. Deny it and hosts on the internet still work; hosts like 192.168.1.10 will not. The wording in that prompt comes from the app: Moshpit connects to servers on your local network over SSH and mosh (UDP). Without this permission, connections to LAN hosts (e.g. 192.168.x.x) will fail.

Step 2

Choose how you sign in

The AUTHENTICATION group is a two-way segmented control: Password or SSH Key. There is no third option — no keyboard-interactive, no certificates, no agent forwarding.

Password

One secure field. The value is saved to the Keychain when you tap Save, and read back before the socket opens on every connect.

SSH Key — two ways

Tapping SSH Key gives you a Key row listing the keys from Settings → SSH Keys, each as name · ALGORITHM, plus an escape hatch at the bottom of the menu: Paste a PEM instead…. Choose a managed key and the connection remembers which one; choose the escape hatch and you get a Private Key (PEM) editor to paste into.

Key types that authenticate: ED25519, RSA, ECDSA P-256, and Secure Enclave P-256 keys, where the signature is produced inside the chip and the private half never exists in memory.

What will not work

  • Passphrase-encrypted private keys. Moshpit never passes a decryption key to the parser, so an encrypted PEM fails. Strip the passphrase from a copy first — ssh-keygen -p -N "" -f ./copy-of-key — and keep the original.
  • ECDSA P-384 and P-521. They are rejected with Unsupported SSH key type: …. P-256 is fine.
  • Hardware tokens. The Add Key screen has a Hardware tab, but it is informational — its confirm button never enables, and ECDSA-sk keys are filtered out of the connection's key menu, because the private half lives on the YubiKey.
  • ProxyJump / bastion hosts, agent forwarding, a startup command. Not in the form, not implemented. A jump host has to be handled on the network side — a VPN or Tailscale.

Face ID, said precisely

This is the one place where the app is easy to over-read, so: a password typed into the connection form, and a PEM pasted into the connection form, are stored without a biometric gate. They are device-only and unlocked-only, but reading them raises no prompt.

Only a key created on the SSH Keys screen with Require Face ID turned on (it is on by default) is stored behind .userPresence — Face ID, Touch ID or the device passcode, on every read. If Face ID matters to you, make the key there and point the connection at it.

Two consequences worth knowing. The credential is read before the socket opens, so on a gated key the Face ID sheet appears first and the host-key prompt second. And the decrypted secret is cached in memory only while the app is in the foreground — Moshpit clears that cache on every backgrounding, precisely so "authenticate on every read" does not quietly become "once per launch". Coming back to a dropped session will ask again.

Step 2b

Generate or import a key

Settings → KEYBOARD · KEYS → SSH Keys. Two groups: THIS DEVICE · SECURE ENCLAVE for hardware-backed keys, and IMPORTED for everything you brought with you. ＋ opens Add Key, which has three tabs.

Generate

Name, an algorithm — ED25519 (marked REC), ECDSA-sk, RSA-4096 — and an optional comment. Under PROTECTION: Require Face ID and Store in Secure Enclave. Turning the Enclave on forces ECDSA P-256, because that is the only curve the chip signs with; the algorithm control follows along.

ED25519 is the recommendation and the default. Choosing ECDSA-sk here fails on purpose — those keys are generated by the token, not by the phone.

Import

Name, comment, a PEM editor expecting -----BEGIN OPENSSH PRIVATE KEY-----, and an optional public key line used to compute the fingerprint.

Get the public half onto the server

Long-press the key row: Copy Public Key, Copy Fingerprint, Share Public Key, Delete Key. That context menu is the only route out of the app for a public key, so it is the step people miss. Paste the line into the server's ~/.ssh/authorized_keys:

# on the host, with the line from Copy Public Key on your clipboard
mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo 'ssh-ed25519 AAAAC3Nza… phone' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

The fingerprint shown in the app is the same shape OpenSSH prints — SHA256: plus unpadded base64 of the SHA-256 over the public blob — so you can compare it against ssh-keygen -lf -E sha256 the-key.pub character for character.

Four honest notes about this screen

  • The Passphrase fields do not encrypt anything. Passphrase and Confirm Passphrase drive the strength meter and the match check, and nothing else — they are never handed to the key generator or to the Keychain. Generated ED25519 keys are written with cipher none. What protects the key is the Keychain plus Face ID, not that field. Do not treat an Moshpit-generated key as passphrase-protected.
  • Bind to hosts is display-only. The chips are stored and drawn, but nothing reads them when choosing a key. Pick the key on the connection instead. (The group's footer mentions an "SSH Keys detail page" that does not exist yet either — rows have a context menu, not a detail screen.)
  • An imported ECDSA key is recorded as ECDSA-sk, and ECDSA-sk is filtered out of the connection's key menu — so an imported P-256 key will not appear there. Paste that PEM straight into the connection form, where P-256 works.
  • Secure Enclave keys cannot be exported, by design. Copy the public key when you make it; there is no second chance to extract the private half.

Step 3

Trust the host fingerprint

Moshpit does trust-on-first-use, the same model as OpenSSH's known_hosts. The first handshake to a host and port pauses and asks. Nothing is trusted automatically.

First contact

New Host

First connection to db-01.example.com:22.

Key fingerprint:
SHA256:8kQ2n…

Verify it matches the server (e.g. `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`).

                          [ Cancel ]   [ Trust ]

Run that command on the host — over a console, an existing session, your provider's web terminal, anything that is not the connection you are trying to verify — and compare. Moshpit shows you the fingerprint; it cannot check it for you.

When the key changes

⚠️ Host Key Changed

The key for db-01.example.com:22 does NOT match the one stored on this device.
This can mean the server was reinstalled — or that the connection is being intercepted.

Stored: SHA256:8kQ2n…
New:    SHA256:pR7wY…

              [ Disconnect ]   [ Trust New Key ]

Note which button is which. Disconnect is the cancel action — the one the dialog treats as safe and the one a stray tap lands on. Trust New Key is styled destructive, because accepting overwrites the stored fingerprint permanently. A rebuilt server and a machine-in-the-middle produce the identical dialog; only you can tell them apart.

How trust is stored

  • Fingerprints live in the Keychain, not in UserDefaults. A pre-seeded entry in a restorable plist would let an intercepted key classify as already-trusted and connect silently, so the map is kept somewhere a backup cannot write to.
  • Entries are keyed by host and port together. The same machine on 22 and on 2222 is two entries, and will prompt twice.
  • The fingerprint is computed over the full SSH wire encoding including the ssh-… header, which is what makes it comparable to OpenSSH's output.
  • If nothing is on screen to answer the prompt, the handshake fails. Both handlers default to deny; there is no path where an unanswered prompt becomes a trusted host.

The limitation: there is no known-hosts screen

Moshpit cannot list the hosts you have trusted, cannot show you their fingerprints after the fact, and has no "forget this host". Deleting a connection leaves its fingerprint behind. After a legitimate re-key — a rebuild, a migration — the only route in the app is to read both fingerprints in the warning dialog and accept the change there.

And because trust is device-only and excluded from backups, a new phone starts from zero: every host prompts again on its first connection. That is the same property that keeps a restored backup from carrying a planted fingerprint, so it is a trade, not an oversight — but it is worth knowing before you set up a second device.

Step 4

Pick a multiplexer

Under ADVANCED, the Multiplexer row offers three choices, each with a one-line description in the menu: None — Single shell, no session persistence; tmux — Mature, already on nearly every host; herdr — Built for coding agents — agent status needs no hooks.

tmux

already on your box

  • Sessions, windows and panes render natively over control mode
  • Attaches to what is already running; never restyles it
  • Agent status needs a one-line hook install on the host
  • Path field: Custom tmux Path

herdr

built for coding agents

  • Agent state is part of the protocol — nothing to install on the host
  • Workspaces and tabs, one full-width pane
  • Isolated tasks: a git worktree, a workspace and an agent from one sheet
  • Path field: Custom herdr Path

Pick None and you get a single plain shell: no session survives a disconnect, and there is nothing for Moshpit to report as missing. Connections saved before this picker existed have no multiplexer field, so they fall back to the old useTmux flag — which the old form always set to true. They come back as tmux, which is what they always did.

They are not interchangeable

tmux and herdr are separate servers holding unrelated sessions. If you pick one and the host only has the other, Moshpit says so and drops to a plain shell. It does not attach the other one — that would show you somebody else's work and label it yours. The rule is stated in the form's own footer, in the degrade logic, and in the design doc.

The custom path field is a loaded gun

The path field follows whichever multiplexer is selected, and filling it in means you vouch for that binary: a non-empty path skips the capability probe entirely. Get it wrong and there is no banner and no graceful degrade — you get the remote shell's raw command not found.

The form ships these fields empty for exactly that reason. An earlier build prefilled the Apple-Silicon Homebrew path for mosh-server, and every Linux host then bypassed the mosh degrade and died on a raw error. Leave them empty unless the binary genuinely lives outside PATH and outside the five directories the probe adds.

Over mosh, both run their own TUI

Mosh's protocol cannot carry tmux control mode or herdr's frame protocol. Turn on Use Mosh with a multiplexer selected and you still get tmux or herdr — as their own full-screen text UI inside the mosh shell, driven by their own prefix keys. What you give up is native pane rendering: the terminal shows the multiplexer's own screen, sidebar and all. The form says so in the ADVANCED footer.

You do not give up the native sheets. Over mosh, Moshpit opens a second, lightweight SSH connection purely for the control plane — tmux's -CC sidecar, or a herdr api snapshot poller — so the Sessions / Workspaces sheet, the Windows / Tabs sheet, the home tree and the breadcrumb keep working. It dials the host the mosh bootstrap already authenticated, so the trust decision is cached and no fingerprint prompt appears for it. If that ever stopped being true, that sidecar is left denying by default: you would lose the breadcrumb rather than silently trust a new key.

The prefix keys are not the same keys

herdr's default prefix is ⌃B, same as tmux — the bindings behind it are not. One of them will cost you: ⌃B q shows pane numbers in tmux and detaches in herdr. herdr picks workspaces with ⌃B w and steps through tabs with ⌃B n / ⌃B p, where tmux uses ⌃B s and ⌃B 1-9. Moshpit's own sheet footers print whichever pair belongs to the connection you are on, so read those rather than your tmux muscle memory.

Three herdr limits worth knowing up front

  • Direct attach is exclusive per pane, and Moshpit attaches with --takeover — it has to, or a reconnect would collide with its own stale attachment. Two Moshpit clients on the same pane therefore evict each other, because only one of them can hold that pane. Moshpit counts the evictions it did not ask for: three inside 30 seconds and it backs off for 30 seconds and says so — Another client is using this pane — retrying shortly — instead of trading the pane back and forth every couple of seconds while your keystrokes land on a channel that was just evicted. It recovers on its own once the other client goes away. The exclusivity is herdr's, not something the client can paper over. A desktop herdr TUI does not hold an attach owner, so laptop-TUI plus phone should be fine — we have not verified that combination on real hardware yet, and we would rather say so.
  • herdr 0.7.3 — the Homebrew stable as of 2026-08-07, protocol 16 — does not report a pane's command, so the breadcrumb falls back to pane 1, pane 2 and so on. Newer builds carry the field.
  • herdr only knows about agents running in its own panes. Its agent status is free because herdr is the runtime those panes live in — it is not a process scanner. A Claude Code you started in a plain SSH shell, or in tmux on the same box, does not appear in the Agents list and does not light up the island. Start it in a herdr pane (or from New Agent Task) if you want it tracked.

Step 5

When the host is missing something

A missing dependency never blocks the connection. Moshpit probes once over the first SSH channel, degrades to something that works, and tells you what it gave up.

What the probe looks at

ssh host command runs a non-login, non-interactive shell, which never sources .zprofile or .bash_profile — so a perfectly good Homebrew tmux would otherwise probe as missing. The probe therefore searches PATH plus five directories:

/opt/homebrew/bin  /opt/homebrew/sbin  /usr/local/bin  /usr/local/sbin  $HOME/.local/bin

$HOME/.local/bin is there for herdr specifically: its installer drops the binary there and deliberately touches no rc file. A tool installed anywhere else will read as missing — that is the probe's blind spot, and the custom path field is the answer to it.

The degrade matrix

You pickedThe host has no…What happens
tmux over SSHtmux Plain single SSH pane, plus a banner
herdr over SSHherdr Plain shell, plus a banner — never tmux
Moshmosh-server Reuses the SSH session you already authenticated, plus a banner; the card's MOSH pill goes grey with a ⚠
Mosh + a multiplexerthe multiplexer Bare mosh shell — no attach line is sent, and no sidecar retries in the background
None— Nothing to miss, no banner

Degrading is per session. The next connect re-probes and comes back at full capability if you installed the thing in between.

The banner and the Install Assist sheet

A degraded session shows one dismissible banner at the top of the terminal — tmux not found on this host — plain SSH session., herdr not found on this host — plain shell session., or mosh-server not found — connected over SSH instead. — with an Install … button. The terminal behind it works normally.

The sheet is titled Install on host and leads with the promise it keeps: Moshpit never installs anything silently. Run the command below in your shell — sudo and its output stay fully visible. Then a command, built for the package manager the probe found:

apt-get   sudo apt-get install -y tmux mosh
dnf / yum sudo dnf install -y tmux mosh
pacman    sudo pacman -S --noconfirm tmux mosh
apk       sudo apk add tmux mosh
brew      brew install tmux mosh

herdr is in no distro repository, so it gets its own installer:
brew      brew install herdr
otherwise curl -fsSL https://herdr.dev/install.sh | sh

tmux and mosh are offered in one command, so a bare host is fixed in one trip. Which packages you are offered comes from the connection's own multiplexer, not from what happens to be missing: a tmux connection gets tmux mosh, and a herdr or None connection that is only missing mosh-server gets mosh alone — a herdr user is never handed a tmux install command. If no package manager is detected, the sheet says Couldn't detect a package manager. and gives generic guidance rather than a command that would fail. herdr is the exception: its installer script needs no package manager, so there is always something to offer.

Three buttons: Run in terminal pastes the command into the live shell and presses return, so the sudo prompt and every line of output stay on screen; Copy command; Re-check re-runs the probe. Re-check answers with Installed — reconnect to enable it. and a Reconnect button, or Still not detected. Run the command, wait for it to finish, then re-check.

For herdr installed outside Homebrew, the sheet adds: Installs to ~/.local/bin. Moshpit looks there when probing and launching, so you don't need to change PATH.

Where re-check does not work

Over mosh there is no SSH channel left to probe on — the bootstrap channel closes once mosh-server takes over. Re-check says Can't re-check over this transport — reconnect to apply. and offers Reconnect, which is the real fix anyway.

One more rough edge, deliberately chosen: the probe result is cached per connection, so a host you last saw as missing tmux may flash the banner for a moment on the next connect before the fresh probe clears it. A stale "everything is present" would be the worse failure, so the cache errs the other way.

Empty terminal, two different messages

After about four seconds of Attaching tmux… (or Attaching herdr…) the terminal resolves to one of two states, and they mean different things. One says the multiplexer is not installed on this host and offers an Install button. The other says there is nothing running: This server has no running sessions. Moshpit only attaches — create the first one to start., with a Create Session button. Binary missing versus nothing running — do not treat them as the same problem.

Those words follow the multiplexer, because herdr does not have sessions. On a herdr connection the same screen reads No herdr workspaces / This server has no running workspaces., and the button says Create Workspace. The whole app does this: tmux has sessions, windows and panes; herdr has workspaces, tabs and panes, and destroying one is Close rather than Kill.

The rules

What Moshpit never does

Three promises the setup path is built around. They are in the source, in the form's own footer text, and in the design docs — not just here.

Install

Never installs silently

Every install command is shown before it runs, and runs in your visible shell, sudo prompt and all. Moshpit fills in the command; you press the button.

Sessions

Never creates or restyles sessions on its own

It attaches to what is already running and leaves the configuration alone. A session is created only when you tap Create Session, and only sessions created through Moshpit get its native look — status bar hidden, restored on disconnect.

Multiplexer

Never switches your multiplexer

Pick herdr on a host that has only tmux and you get a plain shell and a banner — not somebody else's tmux sessions dressed up as yours.

If it does not connect

Reading the error

Connection failures surface in an alert titled Connection Error. The messages are rewritten from the raw library errors so they say something actionable.

What you seeWhat to check
Couldn't reach the server. Check the host, port, and that it's online. DNS, firewall, the port. On a LAN address, whether you denied Local Network permission.
Authentication failed — the server rejected your username and password / key. The username, and whether the public key is really in authorized_keys for that user.
The server rejected this sign-in method. The host has that method disabled — e.g. PasswordAuthentication no. Switch to a key.
Unsupported SSH key type: … ECDSA P-384/P-521, or a PEM the parser could not read. Try an ED25519 key.
Couldn't read the saved credential. The Keychain item is gone — typically after re-installing or re-signing the app. Open Edit and re-enter the password, or re-pick the key.
Connected, but the server wouldn't open a session channel. Auth succeeded; the account is restricted or out of channels server-side.
Does it keep watching my agents when the app is in the background?

No. iOS suspends the app, its keepalive timer and its polling, so agent state stops updating until you come back — the island and the agent list catch up one poll after you return. There is no push server, because there is no Moshpit server at all. It is the honest cost of having nothing in the middle.

Why did it ask for Face ID again?

The decrypted credential is cached in memory only while the app is in the foreground; every backgrounding clears it. Otherwise a key configured to authenticate on every read would quietly become "once per launch". A reconnect after backgrounding re-reads the key from the Keychain, and that prompts.

It dropped. Do I have to do anything?

Usually not. On an SSH session, Moshpit probes the transport every 12 seconds while the app is in the foreground and reconnects on its own; a tmux re-attach lands you back on the pane you were on, with the server-side scrollback intact. herdr re-attaches to the focused pane, but its frame protocol sends screen repaints rather than a byte stream, so there is no local scrollback to restore — history is paged from the server as you scroll. Mosh is exempt from the probe entirely; it handles its own resume and roaming over UDP. If the app was in the background for more than 20 seconds it skips the probe and reconnects outright, because iOS has almost certainly killed the socket already.

Can I use the same key for several hosts?

Yes — pick it in each connection's Key row. Deleting one of those connections will not delete the key, because the secret belongs to the key, not to the connection. The Bind to hosts chips on the key itself are not consulted by anything yet, so ignore them for now.

I changed the port. Why is it asking about the host key again?

Trusted fingerprints are keyed by host and port, so host:22 and host:2222 are separate entries. Verify it and trust it again.
