Troubleshooting

Organised by what you see, not by what went wrong underneath. Every entry says what the screen means and what to do next. Several of them end in "nothing, this is a limit" — those are the honest ones.

Three rules shape almost everything on this page, and knowing them explains most of what you will run into.

You always get connected

A missing dependency never blocks the connection. It degrades. SSH is the floor transport, a bare shell is the floor experience, and the terminal stays fully usable behind any banner.

Plain language, not stderr

Offhook says what is missing, what it costs you, and how to install it. A raw command not found is a bug, not a message.

Nothing happens behind your back

No silent installs. No silent session creation. No quietly attaching the other multiplexer because the one you picked isn't there.

Three surfaces to read before anything else.

The banner at the top of the terminal. One slot, one banner at a time, always dismissible. Precedence is fixed: a dead mosh return path outranks the roaming banner, which outranks the degraded-host banner.

The transport pill in the top bar. It reads SSH or MOSH when live, MOSH · roaming while roaming, reconnecting with an amber dot, or offline with a red one. A dropped session is visible, not silent.

Long-press that pill on a mosh session. You get MOSH DIAGNOSTICS — four raw counters, meant to be screenshotted and sent, not admired.

Missing on the host

A banner says something isn't installed

Offhook probes the host once over the first SSH channel and caches the answer per connection. A missing tool degrades the session it is in and nothing else — install it and the next connect comes back at full capability.

"tmux not found on this host — plain SSH session."

What it means. The capability probe walked PATH on the host and did not find tmux. You are on a single plain SSH pane. Session persistence and the native Sessions / Windows / Pane sheets are off for this session.

What to do. Tap Install tmux in the banner. Install Assist opens with the command for whichever package manager the probe found — apt-get, dnf, yum, pacman, apk or brew. Three buttons, no fourth: Run in terminal pastes the command into the visible shell and presses return, so the sudo prompt and all the output are yours to watch; Copy command hands it over; Re-check re-runs the probe. On success it offers Reconnect.

If the probe recognised none of those six, there is no command to show. The sheet says "Couldn't detect a package manager." and drops to generic guidance plus Re-check rather than guessing at a line that would fail.

tmux and mosh are offered in one command, because a host missing one is usually missing the other. Which packages get named comes from the connection's own multiplexer choice, so a herdr connection is never handed a tmux install line.

"herdr not found on this host — plain shell session." — but tmux is installed

What it means. Exactly what it says. Offhook did not fall back to tmux, and it never will.

Why. tmux and herdr are separate servers holding unrelated sessions. Quietly attaching the one that happens to be installed would show you work that is not the work you asked for.

What to do. Tap Install herdr. herdr is in no Linux distribution repository, so Offhook never synthesises sudo apt-get install -y herdr — that fails with "unable to locate package" and reads as our bug. You get one of two:

brew install herdr                            # Homebrew
curl -fsSL https://herdr.dev/install.sh | sh  # everywhere else

Because the installer needs no package manager, there is always a command to offer for herdr even when no package manager was detected. When you get the script line rather than the Homebrew one, the sheet adds: "Installs to ~/.local/bin. Offhook looks there when probing and launching, so you don't need to change PATH." The official installer really does drop the binary there and deliberately touches no rc file, so its own "not in your PATH" warning is expected — it is not a failure.

"mosh-server not found — connected over SSH instead."

What it means. The probe did not find mosh-server, so Offhook reused the SSH session it had already authenticated and gave you a shell over TCP. You lose roaming; you lose nothing else. The connection's card on the home screen also turns its MOSH pill grey with a warning triangle, so the card is not claiming roaming it does not have.

What to do. Tap Install mosh. If the connection also uses tmux, one command installs both. The fallback keeps your multiplexer: with tmux it still boots tmux -CC, and with herdr it runs the native single-pane frame channel — which is the one thing mosh could not have carried anyway. If the multiplexer is missing as well, you get a bare shell and still only one banner: the mosh one already opens the same Install Assist sheet, so Offhook does not stack a second on top.

The binary is definitely installed, and the banner still says it isn't

What it means. ssh host command runs a non-login, non-interactive shell. It never sources .zprofile or .bash_profile, so anything brew shellenv added to your PATH is invisible over that channel — the exact binary that works when you log in by hand probes as missing. This has been seen live on a macOS/Homebrew host.

What Offhook already does. It prepends the same five directories to both the probe and the launch, so a tool found by one is reachable by the other:

/opt/homebrew/bin   /opt/homebrew/sbin   /usr/local/bin   /usr/local/sbin   $HOME/.local/bin

What to do. If your install is somewhere else, set an explicit path in the connection form: Custom tmux Path, Custom herdr Path, or mosh-server path. The catch, stated plainly: an explicit path means you have vouched for the binary, so it skips the probe's degrade check entirely. A wrong path gives you a raw remote failure instead of a banner. That is also why the fields ship empty — an earlier build prefilled the Apple-Silicon Homebrew mosh path and made every Linux host bypass the graceful degrade.

Re-check says "Can't re-check over this transport — reconnect to apply."

What it means. You are on mosh. The bootstrap SSH channel is closed the moment mosh takes over, so there is no live channel left to probe. Offhook returns "no new information" rather than probing a dead session, which would falsely read as "everything is installed".

What to do. Tap Reconnect in the same sheet. A reconnect re-runs the probe from scratch, so anything you installed in the meantime is picked up without touching a setting.

The banner arrives a moment after the terminal does

What it means. The degrade decision waits for the probe. The shell paints as soon as SSH is up; the banner is raised only once command -v has answered over that first channel, one round trip later. Nothing is guessed in the gap and nothing flashes — the cached verdict is used to populate Install Assist, not to raise or clear the banner.

The one place a stale answer shows through. If the probe cannot run at all, Offhook keeps what it last knew rather than assuming everything is present. A cache entry written by a build that predates herdr support has no herdr field in it and is read as "herdr missing" — deliberately, because a stale "present" would launch a binary the host does not have, and a stale "missing" costs one banner that the next successful probe clears.

Why not the optimistic default. A probe that cannot run returns "no new information". Upgrading a known-degraded host back to "all present" would send it straight into tmux -CC attach on a box with no tmux, which never returns.

What to do. Nothing, unless you fixed the host in another window — the probe runs once per connect, so reconnect to pick it up.

Nothing is painting

Black screen, spinner, or an empty state

Several unrelated causes that look nearly identical on a phone. The difference is which surface tells you the truth.

Mosh: black screen, live cursor, no error

What it means. The UDP socket reached ready and Offhook kept flushing, but zero reply datagrams ever came back. The return path is dead — almost always a VPN, proxy or firewall on the network you are on right now, passing your outbound UDP and dropping the server's replies. It is not a decode bug and not a dead server. SSH rides TCP over the same path and works.

What you see, after eight seconds. A watchdog arms once the connection is ready and flushing, and fires at most once:

⚠  Mosh isn't receiving data — your network may be
   blocking UDP (VPN, proxy, or firewall).

   Switch to SSH                                    ×

The deadline is deliberately generous. The first reply is one round trip after the first flush, so even a multi-second-latency link answers well inside eight seconds — only a link that returns nothing runs it out. The watchdog retires the instant any datagram lands, including one that fails to decrypt or parse, so a working-but-slow link never trips it. It only ever arms before the first datagram: a mid-session stall is a different problem, often recoverable through roaming, and is left alone.

What to do. Tap Switch to SSH. It flips the connection's protocol, saves it, and reconnects over TCP through the same path that ate your UDP. The terminal was never blocked — keystrokes were reaching the server the whole time, only the rendering was starved — so the × just dismisses the banner and leaves the mosh session as it was. To fix the path instead: UDP 60000–61000 inbound on the server and outbound from your phone, and check whether your VPN or proxy is the thing eating it.

How to confirm it is the return path and not something else

Long-press the transport pill on a mosh session for MOSH DIAGNOSTICS. If it reads "No datagrams yet.", that is the tell — nothing has come back at all. Otherwise you get four counters:

datagrams Total UDP datagrams received, counted before decrypt or parse. A low number behind a connected pill points at the network or NAT, not at the app.

applied The highest display state actually applied. Stuck at 0 while datagrams arrive means every diff so far hit the gap or parse-failure branch.

parse fails Host messages that failed to parse on an otherwise applicable diff.

gaps Diffs that arrived out of order. Occasional gaps are expected on a lossy link. A count that keeps climbing while applied never advances means the client is stuck re-diffing.

This overlay exists because the failure it diagnoses needs real packet loss, real reordering, or one specific remote's shell config to reproduce, and none of that happens on a loopback test. A screenshot of it is the most useful thing you can attach to a report.

A host on your own LAN behaves differently from one on the internet

What it means. iOS Local Network permission was denied for Offhook. Hosts on the internet are unaffected; hosts like 192.168.1.10 are gated by that switch. Offhook's own prompt says it plainly, and it covers both transports: "Offhook connects to servers on your local network over SSH and mosh (UDP). Without this permission, connections to LAN hosts (e.g. 192.168.x.x) will fail."

What to do. iOS Settings → Offhook → Local Network, and turn it on. The app declares the permission for this one reason and asks for it on first use. Check it before anything else on a LAN address — it is one switch and it rules out the whole class, including the case where SSH connects and only mosh sits black.

"No tmux sessions" / "No herdr workspaces", with a Create button

What it means. The binary is installed and reachable. The server simply has nothing running. The panel says it outright, in whichever noun the multiplexer uses: "This server has no running sessions / workspaces. Offhook only attaches — create the first one to start."

Why the app doesn't just make one. Offhook never creates or restyles a session on its own. With tmux it attaches to sessions you already have and leaves them exactly as they are; only the sessions you create through Offhook get Offhook's own look — status bar off — and that is restored on disconnect.

What to do. Tap Create Session or Create Workspace. The button reads Creating… while the command is in flight. On herdr, that one tap also starts the server if it isn't running — a genuinely cold herdr server comes up with zero workspaces, so Offhook starts it and then creates the first workspace, and only ever from that explicit tap.

Stuck on "Attaching tmux…" or "Attaching herdr…"

What it means. The first few seconds are the normal attach handshake. The spinner holds for four seconds before Offhook is willing to say anything, then it settles into one of exactly two honest answers: "tmux not installed on this host" with an Install button, or "No tmux sessions" with a Create button. The panel exists to kill a specific mis-diagnosis: without tmux, tmux -CC attach never returns, the screen used to sit on "Attaching tmux…" forever, and the empty state then falsely reported "No tmux sessions" — where Create Session would have failed too.

What to do. Wait past four seconds and read which of the two you got. If it is a tmux connection, a second, longer deadline is running on the home screen at the same time: a control-mode attach that has not confirmed within 22 seconds turns that connection's card amber, replaces the spinner with "Attach didn't complete — tmux never confirmed.", and offers RETRY. SSH is still up at that point, so it is a stalled attach, not a dead host. The 22 seconds are sized for a slow link: a normal attach on a high-latency host was measured at 10–20 seconds with no progress feedback at all, which reads as "stuck" long before it is. herdr has no equivalent deadline — on that path the four-second panel is the whole story.

herdr: black screen, no empty state, and the Tabs sheet's + does nothing

What it means. herdr is installed but its server is not running, and you are on a build that could not tell. This was a real shipped bug. Offhook detected the condition by matching herdr 0.8.0's structured {"error":{"code":"server_not_running"}}, but herdr 0.7.3 — what brew install herdr gave us in August 2026 — emits a bare Rust error instead:

Error: Os { code: 2, kind: NotFound, … }

The text never matched, the "server not running" flag stayed false, and the empty state never showed. Worse, the SSH layer merges stderr into stdout and drops the exit code, so nothing on screen indicated the command had failed at all.

The fix, and the lesson. Stop matching error text entirely. Every herdr command now carries ; echo "__offhook_rc=$?" and the decision is made on the exit code, which is 1 in both versions. Cross-version detection has to pick the most stable signal available, and error strings are the least stable one there is.

What to do. Update. A herdr server that isn't running is an empty state with a Create Workspace button — it is not a connection failure and is not treated as one.

The pane breadcrumb says "pane 2" instead of the command

What it means. herdr 0.7.3 (protocol 16) does not report a pane's command, title or label — those fields arrive in 0.8.0 (protocol 19). The snapshot decoder is written so a missing field degrades that one detail rather than failing the whole read, so the crumb falls back to pane N.

Why it doesn't just disappear. The pane crumb is the only entry point to the Select Pane sheet. A vanished crumb would take pane switching with it.

What to do. Nothing you need to. Note the related gap while you are here: because 0.7.3 reports no agent name either, idle agent rows never appear in the Agents section on 0.7.3.

Over mosh you get herdr's own sidebar, or tmux's own status line

What it means. This is by design and it cannot be fixed. mosh transmits rendered screen diffs, so it cannot carry a line-framed control protocol — neither tmux -CC nor herdr's frame protocol survives it. Verified empirically: tmux -CC starts server-side over mosh and no %begin or %output ever comes back.

What you actually get. The multiplexer runs its own full-screen TUI inside the mosh shell and Offhook is just the renderer. A separate lightweight SSH connection runs alongside to feed the native sheets: rendering over UDP, control over TCP. On a phone, herdr's own sidebar takes roughly a third of the screen width — usable, but cramped. That is precisely why the native single-pane frame channel exists on SSH.

What to do. If you want native rendering, use SSH for that connection. The Add Connection form says so before you connect: "With Mosh, herdr runs its own terminal UI; native rendering needs SSH."

It was fine, then it wasn't

Drops, contended panes, and stale state

These are the ones where the answer is most often a limit rather than a fix. They are written down here so you do not have to discover them by filing a bug.

"Another client is using this pane — retrying shortly"

What it means. herdr's direct attach is exclusive per terminal. Its terminal_attach_owners refuses a second attacher unless that attacher passes --takeover, and Offhook always passes it, because a reconnect necessarily collides with its own stale attach. So two Offhooks pointed at the same pane evict each other.

What Offhook does about it. The control poller re-reports the focused pane after every poll, not only when the focus changes. That repeat is what heals a channel someone else evicted. Before that fix, the evicted client went black and never recovered, because retarget only ran on a focus change and the focus had not changed — and an eviction moves nothing in the tree, so nothing looked different. For the same reason a lost attach also drops the poller back to its fast cadence and reads immediately, instead of waiting out an idle interval.

After three evictions inside a 30-second window, Offhook stops re-attaching for 30 seconds and shows this notice. It clears itself the moment a frame paints again.

The limit, plainly. Two directly-attached clients will fight each other, each reclaiming the pane on its next poll — every couple of seconds while anything is moving. That is inherent to herdr's exclusive direct attach and cannot be fixed on the client side. Put the second client on a different pane, or close it.

One thing we have not verified. A laptop running herdr's own TUI does not occupy an attach owner, so "laptop on the TUI, phone on Offhook, same host" should not conflict. We have not tested it, so we are not claiming it works.

You come back to the app and the agent state is stale

What it means. iOS suspends the app in the background, including its SSH polling. Agent state stops updating until you return, and catches up one poll after you re-foreground. Measured on device: flipping a pane from blocked to working while the app was backgrounded left the Dynamic Island unchanged until the app came forward.

Why there is no fix. There is no push server, because there is no Offhook server at all. Alerts are generated on-device from the live session; they fire while the app is in the foreground or recently backgrounded, and a fully suspended app does not poll. This is identical on the tmux path — it is not a herdr problem.

The lock-screen Live Activity carries a 120-second stale date, so two minutes without a push from the app lets it render an honest "paused" hint instead of a frozen "working".

What to do. Open the app. That is the whole remedy, and it is the cost of having nothing in the middle.

Something you did on your laptop takes seconds to show up on the phone

What it means. herdr's control plane is polled, not pushed. The poll runs every 2 seconds while anything is moving and eases to 8 seconds after three identical reads; any change or a manual refresh snaps it back to 2 seconds. Actions you take in the app are followed by an immediate re-read and feel instant. Actions taken anywhere else can lag by up to 8 seconds.

Why polling. herdr's socket API does have events.subscribe, with 26 event types. The CLI never exposes a general subscribe subcommand — it has api snapshot and api schema, plus a wait that is scoped to one pane and one status — and a phone cannot open the host's Unix domain socket. Polling is the only mechanism that covers the whole tree. It is also how agent state reaches the Dynamic Island, which is why the idle ceiling is 8 seconds and not something more frugal.

A consequence worth knowing. Elapsed times in the Agents section are only ever shown to minute granularity — now, 2m, 1h 12m. The number behind them carries up to eight seconds of error, and printing seconds would claim a precision it does not have.

The pill says "reconnecting" or "offline"

What it means. The session dropped and Offhook is handling it. While the app is in the foreground it probes the transport every 12 seconds; the probe itself round-trips a trivial command with an 8-second timeout. If it fails, the session marks reconnecting and reconnects. If it is already reconnecting, the next 12-second tick retries, which is what acts as the backoff.

The 8-second probe timeout is tuned, not arbitrary: a false "dead" tears down a working session and forces a full SSH re-handshake, which on a slow link costs 6–9 seconds. Genuinely dead sockets still fail fast on a write error.

What to do. Usually nothing. A tmux attach reattaches to the same server-side session, so panes and their scrollback come straight back, and you land on the pane you were on. Mosh is exempt from the SSH probe entirely — it owns its own UDP resume and roaming.

You were away for a minute and it reconnected instead of resuming

What it means. Backgrounded for longer than 20 seconds, Offhook skips the liveness probe on return and forces a fresh reconnect. iOS has almost certainly killed the TCP socket by then, and the probe can false-positive on a half-open channel — the result of trusting it is a green pill over a frozen pane.

Backgrounding also stops the keepalive timer (iOS would suspend it anyway) and hands every tmux window-size pin back to the server, so a desktop client attaching while you are away gets its full width instead of the phone's grid.

It asked for Face ID again

What it means. Every backgrounding drops every decrypted secret Offhook was holding in memory. Re-foregrounding forces a fresh, biometry-gated read from the Keychain, and that is what prompts.

Why. A key configured to authenticate on every read would otherwise quietly become "once per app launch". The reconnect after a backgrounding re-reads the credential, so the prompt lands there.

An agent you are definitely running does not appear in the Agents section

First, the section only exists on herdr connections. A tmux connection's card has no Agents section at all — that data depends on whether you installed Offhook's status hook, and a list that silently omits half your agents is worse than no list.

On herdr. The section lists agents inside herdr's own panes, not every agent process on the machine. A claude you started in Terminal.app is invisible to it. herdr is a runtime, not a process scanner: it identifies agents by watching the panes it owns, and herdr integration install claude makes the agent report itself rather than being recognised on screen — more authoritative, still only for panes herdr holds.

What to do. Start it through New Agent Task, or run it inside a herdr pane. Either way it shows up on the next poll.

One version gap. On herdr 0.7.3 a pane carries no agent name, so an agent sitting idle produces no row — there would be nothing to label it with. An agent that is working or blocked still appears; the row just falls back to a generic name.

A prefix chord dropped the whole session

What it means. tmux and herdr both default to Ctrl-b as the prefix, and they do not agree on what follows it. ⌃ b q lists panes in tmux and detaches in herdr. ⌃ b s opens the session list in tmux and is unbound in herdr, where workspaces are ⌃ b w. tmux jumps to a window with ⌃ 1-9; herdr steps with ⌃ b n / ⌃ b p.

Where this can bite you. Only where the multiplexer's own full-screen UI is what you are looking at — over mosh, or in a shell where you started herdr / tmux yourself. On the native paths Offhook drives the multiplexer over its own channel and your keystrokes go to the pane, so the prefix never reaches it.

What to do. Detach is not kill: the workspace and its panes stay on the server, so reconnecting picks them straight back up. If you build your own prefix key in the shortcut editor, build the one for the multiplexer you actually use. The sheets print the right chord per connection, and the pane sheet on a herdr connection prints ⌃ b v — the split — precisely because herdr has no "show me the panes" key to print.

Still stuck

What to send

There are no users yet and no support queue to hide behind, so a report goes straight to the person who wrote the code. These four things make it answerable in one round trip instead of five.

  • The banner text, verbatim, or a photo of the screen. The wording identifies which branch you hit.
  • A screenshot of MOSH DIAGNOSTICS if the session is mosh. Long-press the transport pill. "No datagrams yet." answers the question on its own.
  • Transport and multiplexer for that connection — SSH or mosh, and none, tmux or herdr. Half the failure modes on this page only exist in one combination.
  • Versions on the host. tmux -V, mosh-server --version, herdr --version. herdr protocol drift between 0.7.3 and 0.8.0 has already caused one black-screen bug, and it will not be the last.

Where to send it is on the support page.
