文档

排障

按「你看到什么」编排，而不是按「底层出了什么问题」。每一条都说清楚这屏是什么意思、 下一步做什么。有几条的答案是「什么都不用做，这就是限制」——那几条才是最诚实的。

这一页几乎所有内容都由三条规则决定，知道了它们，大部分现象自己就解释得通。

一定连得上

缺依赖绝不阻断连接，只降级。SSH 是保底传输，裸 shell 是保底形态； 任何 banner 后面的终端都完全可用。

说人话，不甩 stderr

缺什么、影响什么、怎么装，都说清楚。直接把一句 command not found 甩到你脸上，那是 bug，不是提示。

不背着你做事

不偷装、不偷建会话，也不会因为你选的那个 multiplexer 不在， 就悄悄给你附加另一个。

先看这三处，再谈别的。

终端顶部那条 banner。同一时间只有一条，永远可以关掉。优先级是固定的： mosh 回程断了 > 漫游中 > 主机降级。

顶栏的传输标签。连着的时候显示 SSH 或 MOSH， 漫游中显示 MOSH · roaming，还有琥珀点的 reconnecting 和红点的 offline。掉线是看得见的，不会闷着。

mosh 会话里长按这个标签。会出来 MOSH DIAGNOSTICS——四个原始计数值， 它就是用来截图发出去的，不是用来看好看的。

主机上缺东西

banner 说某个东西没装

Offhook 会在第一条 SSH 通道上探测一次主机，按连接缓存结果。 缺工具只影响当次会话，装好之后下次连接自动回满血。

“tmux not found on this host — plain SSH session.”

什么意思。能力探测走了主机的 PATH，没找到 tmux。 这次会话是一个纯 SSH 单 pane：会话持久化没有了，原生的 Sessions / Windows / Pane 面板也没有了。

怎么办。点 banner 上的 Install tmux，Install Assist 会按探测到的包管理器给出命令——apt-get、dnf、 yum、pacman、apk 或 brew。 只有三个按钮，没有第四个：Run in terminal 把命令粘进当前那个可见的 shell 并回车，sudo 密码提示和全部输出都在你眼前跑；Copy command 只复制；Re-check 重跑探测，成功之后给你一个 Reconnect。

这六个包管理器一个都没探到的话，就没有命令可给。sheet 会写 “Couldn't detect a package manager.”，然后只留一段通用说明加一个 Re-check， 而不是硬拼一条注定失败的命令。

tmux 和 mosh 是同一条命令一起装的——缺一个的主机通常另一个也缺， 一条命令好过两个来回。装哪些包是按这条连接自己选的 multiplexer 决定的， 所以一个 herdr + mosh 的用户不会被塞一条装 tmux 的命令。

“herdr not found on this host — plain shell session.”——可主机上明明有 tmux

什么意思。就是字面意思。Offhook 没有退回去用 tmux，以后也不会。

为什么。tmux 和 herdr 是两个互不相干的 server，装着互不相干的会话。 哪个装了就悄悄附加哪个，等于把「不是你要的那份活」端到你面前，还说这就是你的活。

怎么办。点 Install herdr。herdr 不在任何一个 Linux 发行版仓库里， 所以 Offhook 绝不会拼出 sudo apt-get install -y herdr——那条命令会以 “unable to locate package” 失败，看上去像是我们的 bug。你会拿到这两条之一：

brew install herdr                            # Homebrew
curl -fsSL https://herdr.dev/install.sh | sh  # 其他情况

因为它的安装脚本根本不需要包管理器，所以哪怕没探测到包管理器，herdr 也永远有一条命令可给。拿到的是脚本那条（而不是 Homebrew 那条）时，sheet 还会多一句说明：“Installs to ~/.local/bin. Offhook looks there when probing and launching, so you don't need to change PATH.” 官方安装脚本确实把二进制放在那里，并且刻意不改任何 rc 文件——所以它自己打印的 “not in your PATH” 警告是预期之内的，不代表装失败了。

“mosh-server not found — connected over SSH instead.”

什么意思。探测没找到 mosh-server，于是 Offhook 复用了那条已经认证过的 SSH 会话，直接给你一个 TCP 上的 shell。 你失去的只有漫游，别的都在。首页那张卡片上的 MOSH 标签同时会变灰并挂一个警告三角， 免得卡片继续声称自己有漫游。

怎么办。点 Install mosh。如果这条连接还用了 tmux， 一条命令把两个都装了。降级不会顺手把多路复用器也拿掉：选 tmux 就照样拉起 tmux -CC，选 herdr 就跑原生单 pane 帧通道——而后者本来就是 mosh 承载不了的那一半。要是多路复用器也缺，那就是裸 shell，而且仍然只有一条 banner：mosh 那条点进去就是同一张 Install Assist，Offhook 刻意不在上面再叠一条。

那个二进制明明装了，banner 还是说没装

什么意思。ssh host command 起的是一个非登录、非交互的 shell， 它不会 source .zprofile 或 .bash_profile， 所以 brew shellenv 往 PATH 里加的东西在这条通道上是不可见的—— 你手工登录时明明能用的那个二进制，探测出来就是「没有」。这在一台真实的 macOS / Homebrew 主机上撞到过。

Offhook 已经做了什么。探测和实际启动前置同样这五个目录， 保证「探到的」和「跑得起来的」是同一个：

/opt/homebrew/bin   /opt/homebrew/sbin   /usr/local/bin   /usr/local/sbin   $HOME/.local/bin

怎么办。如果你装在别处，就在连接表单里填绝对路径：Custom tmux Path、 Custom herdr Path，或者 mosh-server path。 但有代价，说在前面：填了绝对路径就等于你为这个二进制背书， 它会完全跳过探测的降级检查。路径写错的结果不是一条 banner， 而是一个原始的远端报错。这也是这几个字段默认留空的原因—— 早期版本预填了 Apple Silicon 上的 Homebrew mosh 路径， 结果让每一台 Linux 主机都绕过了优雅降级。

Re-check 回了一句 “Can't re-check over this transport — reconnect to apply.”

什么意思。你在 mosh 上。mosh 接管之后，那条 bootstrap 用的 SSH 通道就关了，已经没有活着的通道可以再探一次。Offhook 这时返回的是「没有新信息」， 而不是去探一条死会话——那会被误读成「全都装好了」。

怎么办。点同一张 sheet 里的 Reconnect。重连会从头重跑一遍探测， 你中途装的东西不用改任何设置就会被认出来。

banner 比终端晚一步才出来

什么意思。降级这个判断是等探测的。SSH 一通，shell 就画出来了； banner 要等 command -v 在那条通道上回话，也就是一个往返之后。 这中间不猜、也不会先闪一条再改口——缓存下来的结论是拿去填 Install Assist 的， 不负责挂起或撤掉 banner。

唯一会漏出旧答案的地方。探测彻底跑不起来时，Offhook 保留上一次知道的结果， 而不是假设「都装着」。一条由不支持 herdr 的老版本写下的缓存里压根没有 herdr 这个字段， 它会被读成「herdr 缺失」——这是故意的：过期的「有」会去启动一个主机上根本没有的二进制， 而过期的「没有」最多多挂一条 banner，下一次探测成功就清掉了。

为什么不用那个乐观默认值。跑不起来的探测返回的是「没有新信息」。 把一台已知降级的主机升回「全都有」，等于把它直接送进一台没有 tmux 的机器上的 tmux -CC attach——那条命令永远不返回。

怎么办。不用管。除非你刚在别的窗口把主机修好了——探测每次连接只跑一遍， 重连一下才认得出来。

画面不刷

黑屏、转圈，或者一个空状态

四种完全不同的成因，在手机上长得几乎一样。区别在于：哪一处界面会告诉你实话。

Mosh：黑屏，光标活着，没有任何报错

什么意思。UDP socket 已经 ready，Offhook 也一直在往外发， 但一个回程数据报都没收到。也就是回程断了——绝大多数情况是你此刻这张网上的 VPN、代理或者防火墙：放行了你发出去的 UDP，把服务端的回包丢了。 这不是解码 bug，也不是服务端挂了。SSH 走 TCP，同一条路上是通的。

八秒之后你会看到。连接 ready 并开始发包时会武装一个看门狗，最多只触发一次：

⚠  Mosh isn't receiving data — your network may be
   blocking UDP (VPN, proxy, or firewall).

   Switch to SSH                                    ×

八秒是故意给得宽的：第一个回包是在第一次发包之后一个 RTT 到， 所以哪怕是几秒延迟的链路也远远在八秒之内答上话——只有什么都不回 的链路才会把它耗完。只要有任何一个数据报落地，哪怕解不了密、解不了包， 看门狗立刻退役，所以「能通但很慢」的链路永远不会误触发。 它也只在第一个数据报之前武装：会话中途的卡顿是另一回事， 往往能靠漫游自愈，Offhook 刻意不去碰。

怎么办。点 Switch to SSH。它会把这条连接的协议翻成 SSH、存下来、 然后走 TCP 重连——走的正是刚才吃掉你 UDP 的那条路。整个过程终端从来没被挡住过： 你的按键一直在到达服务端，饿着的只有渲染，所以那个 × 只是关掉 banner， mosh 会话原封不动。想从根上修，就把 UDP 60000–61000 在服务端放行入站、 在手机侧放行出站，再看看是不是 VPN 或代理在中间吃包。

怎么确认真的是回程断了，而不是别的毛病

在 mosh 会话里长按传输标签，打开 MOSH DIAGNOSTICS。如果上面写着 “No datagrams yet.”，那就是铁证——一个回包都没有。否则你会看到四个计数器：

datagrams 收到的 UDP 数据报总数，在解密和解析之前就计。标签显示已连接、这个数却很小， 问题指向网络或 NAT，不是 App。

applied 实际应用到屏幕上的最高状态号。数据报在涨、它却卡在 0， 说明到目前为止每一个 diff 都走进了「乱序」或「解析失败」那条分支。

parse fails 本来该应用的 diff，解析失败的次数。

gaps 乱序到达的 diff。丢包链路上偶尔有几个是正常的；但它一直涨、 applied 却始终不动，说明客户端卡在反复重新求差分上。

这个浮层之所以存在，是因为它诊断的那种故障需要真实的丢包、真实的乱序， 或者某一台特定远端的 shell 配置才复现得出来，回环测试一个都碰不到。 报问题时，截这张图是最有用的一件事。

局域网里的主机：SSH 连得上，mosh 黑屏

什么意思。Offhook 的「本地网络」权限被拒了，iOS 会直接把发往局域网地址的 UDP 丢掉。SSH 走 TCP，不受影响——所以这个现象看起来才那么像 mosh 的 bug。 公网主机同样不受影响。

怎么办。iOS 设置 → Offhook → 本地网络，打开。 这个权限存在只为这一件事，首次连接时会问你。

“No tmux sessions” / “No herdr workspaces”，下面一个 Create 按钮

什么意思。二进制装了、也找得到，只是 server 上一个会话都没跑。 那块面板自己写得很清楚：“This server has no running sessions. Offhook only attaches — create the first one to start.”

为什么不干脆替你建一个。Offhook 从不自己创建、也从不自己改造会话。 用 tmux 时它只附加到你已有的会话，并且原样不动；只有你通过 Offhook 亲手创建的会话才会被套上它自己那套外观，而且断开时会还原回去。

怎么办。点 Create Session 或 Create Workspace， 命令在飞的时候按钮会变成 Creating…。在 herdr 上，这一下点击还会顺手把 server 拉起来——一个真正冷启动的 herdr server 起来是零个 workspace， 所以 Offhook 先起 server、再建第一个 workspace，而且只在你这次明确点击时才做。

一直停在 “Attaching tmux…” 或 “Attaching herdr…”

什么意思。头几秒本来就是正常的 attach 握手。转圈会持续四秒， Offhook 在那之前不愿意下任何结论；四秒之后它只会给你两个诚实答案之一： “tmux not installed on this host” 加一个 Install 按钮， 或者 “No tmux sessions” 加一个 Create 按钮。这块面板就是为了干掉一个具体的误诊： 主机没有 tmux 时 tmux -CC attach 永远不返回， 屏幕过去会永远停在 “Attaching tmux…”，然后空状态还谎报一句 “No tmux sessions”—— 而那时候点 Create Session 同样会失败。

怎么办。等过四秒，看看落到了哪一种。高延迟主机上，tmux 控制模式的 attach 最多等 22 秒就放弃，不会既没报错也没出路地一直吊着。

herdr：纯黑屏，没有空状态，Windows 面板上的 + 点了没反应

什么意思。herdr 装了，但它的 server 没跑，而你手上这个版本判断不出来。 这是一个真实上线过的 bug。Offhook 当时是靠匹配 herdr 0.8.0 的结构化 {"error":{"code":"server_not_running"}} 来识别的， 而 herdr 0.7.3——也就是 Homebrew 上当前的稳定版——吐的是一句裸的 Rust 报错：

Error: Os { code: 2, kind: NotFound, … }

文本永远匹配不上，「server 没跑」这个标志一直是 false，空状态从来没出现过。 更糟的是，SSH 那一层把 stderr 并进了 stdout 又丢掉了退出码， 所以屏幕上连「这条命令失败了」都看不出来。

怎么修的，以及教训。彻底不再匹配错误文本。现在每条 herdr 命令后面都挂一个 ; echo "__offhook_rc=$?"，靠退出码判断——两个版本都是 1。 跨版本检测必须挑现有信号里最稳的那个，而错误字符串恰恰是最不稳的那个。

怎么办。升级。一个没在跑的 herdr server 是一个带 Create Workspace 按钮的空状态，它不是连接失败，也不该被当成连接失败处理。

pane 面包屑显示的是 pane 2，不是命令名

什么意思。herdr 0.7.3（protocol 16）不上报 pane 的 command、title 和 label——这些字段是 0.8.0（protocol 19）才有的。快照解码器是按「缺字段就降级这一处细节、 绝不让整份快照失败」写的，所以这一段退回成 pane N。

为什么不干脆不显示。pane 这一段面包屑是打开 Select Pane 面板的唯一入口。 它消失了，切 pane 也就跟着没了。

怎么办。不用做什么。顺带记一笔相关的缺口：0.7.3 同样不上报 agent 名字， 所以在 0.7.3 上，Agents 区里那种「idle 但有名字」的行永远不会出现。

走 mosh 的时候，看到的是 herdr 自己的侧栏、或者 tmux 自己的状态栏

什么意思。这是设计使然，而且修不了。mosh 传的是渲染完的屏幕差分， 承载不了行分帧的控制协议——tmux 的 -CC 和 herdr 的帧协议都活不下来。 实测验证过：tmux -CC 在 mosh 上服务端确实起来了， 但一个 %begin、一个 %output 都没回来。

那你实际拿到的是什么。multiplexer 在 mosh shell 里跑它自己的全屏 TUI， Offhook 只是个渲染器；旁边另起一条轻量 SSH 连接来喂原生面板—— 渲染走 UDP，控制走 TCP。在手机上，herdr 自己的侧栏大约吃掉三分之一的屏宽， 能用，但挤。SSH 上那条原生单 pane 帧通道，存在的理由正是这个。

怎么办。想要原生渲染，这条连接就用 SSH。这件事 App 在你连之前就说了——Add Connection 表单里那句：“With Mosh, herdr runs its own terminal UI; native rendering needs SSH.”

刚才还好好的

掉线、pane 被抢、状态不新

这一组里，答案更多是「这是限制」而不是「这样修」。 写在这儿，是为了让你不必靠提 bug 才发现它们。

“Another client is using this pane — retrying shortly”

什么意思。herdr 的直连附加是按终端独占的。它的 terminal_attach_owners 会拒绝第二个附加者，除非对方带上 --takeover——而 Offhook 永远带着这个参数，因为一次重连必然会和自己那条 stale 的旧附加撞车。于是两台 Offhook 指着同一个 pane 时，会互相把对方踢下去。

Offhook 为此做了什么。控制轮询在每一次轮询之后都重报一遍当前聚焦的 pane，而不只在焦点变化时报。正是这个重复动作，让一条被别人踢掉的通道能自愈—— 大约两秒内恢复。修之前，被踢掉的那一端会黑屏并且永远回不来， 因为重定向只在焦点变化时才跑，而焦点根本没变。

30 秒窗口内被踢掉三次之后，Offhook 会停止重新附加 30 秒，并显示这条提示。 只要有一帧重新画出来，它自己就消失。

限制，直说。两个直连客户端就是会互相打架，各自大约每两秒抢一次。 这是 herdr 独占式直连的固有行为，不是能在客户端消掉的。 把第二个客户端挪到别的 pane，或者关掉它。

有一件事我们没验过。笔记本上跑 herdr 自带的 TUI 并不占用 attach owner， 所以「笔记本开 TUI + 手机开 Offhook，同一台主机」按理不冲突。 但我们没测过，所以不声称它可用。

回到 App，agent 状态是旧的

什么意思。iOS 会在后台挂起 App，连它的 SSH 轮询一起挂起。 agent 状态就停在那里，直到你回来——回到前台之后的第一次轮询会补上。 真机实测过：App 在后台时把一个 pane 从 blocked 翻成 working， 灵动岛纹丝不动，直到 App 回到前台。

为什么没得修。没有推送服务器，因为根本就没有 Offhook 服务器。 提醒是在设备上、从活着的会话里生成的：App 在前台、或者刚切到后台不久时会响， 一个被完全挂起的 App 不会轮询。tmux 那条路完全一样——这不是 herdr 的问题。

锁屏上的实时活动带一个 120 秒的过期时间（相当于漏掉两轮扫描）， 这样它可以老实地显示「暂停」，而不是冻在一个「working」上骗你。

怎么办。打开 App。就这一招，这就是「中间不放任何东西」的代价。

你在笔记本上做的事，手机上要过几秒才看到

什么意思。herdr 的控制面是轮询的，不是推送的。有动静时每 2 秒轮一次， 连续三次读到一样的内容之后放缓到 8 秒；任何变化或者你手动刷新，立刻回到 2 秒。 你在 App 里做的操作后面都跟着一次立即重读，所以是即时的； 在别处做的操作最多会滞后 8 秒。

为什么是轮询。herdr 的 socket API 确实有 events.subscribe， 带 26 种事件类型。但 CLI 从来没暴露 subscribe 子命令——只有 api snapshot 和 api schema——而手机也打不开主机上的 Unix domain socket。轮询是唯一可用的机制。

一个值得知道的后果。Agents 区里的已用时长只精确到分钟—— now、2m、1h 12m。 它背后的数字带着最多八秒的误差，打印到秒就是在声称一个它没有的精度。

标签显示 “reconnecting” 或 “offline”

什么意思。会话掉了，Offhook 正在处理。App 在前台时每 12 秒探一次链路， 探测本身是往返一条微不足道的命令，超时 8 秒。失败就标记 reconnecting 并重连； 如果已经在重连，下一个 12 秒的 tick 会再试一次——这就是它的退避。

8 秒这个超时是调出来的，不是随手写的：一次误判「已死」会拆掉一条本来好好的会话， 并强制一次完整的 SSH 重新握手，在慢链路上要花 6–9 秒。 真正死掉的 socket 依然会在写失败时立刻暴露。

怎么办。通常什么都不用做。tmux 的 attach 重新附加的是服务端那同一个会话，pane 和回滚缓冲原样回来， 并且会把你送回原来那个 pane。Mosh 完全不走这条 SSH 探测——它自己在 UDP 上管恢复和漫游。

离开一分钟回来，它是重连而不是恢复

什么意思。后台超过 20 秒，回来时 Offhook 会跳过存活探测，直接强制重连。 到那个点上 iOS 几乎必然已经把 TCP socket 杀了，而探测在一条半开通道上会误报「活着」—— 信了它的结果就是：绿色标签配一个冻住的 pane。

切后台时它还会停掉保活定时器（反正 iOS 也会挂起它）， 并把所有 tmux 窗口尺寸的钉住交还给服务端， 这样你不在的时候有桌面客户端接上去，拿到的是全宽，而不是手机的网格。

怎么又问我 Face ID

什么意思。每次切到后台，Offhook 都会把内存里所有解密过的凭据丢掉。 回到前台会强制从 Keychain 重新读一次，这一次读是要生物识别的，所以会弹。

为什么。否则一把配置成「每次读取都验证」的密钥， 会悄悄退化成「每次启动验证一次」。切后台之后的那次重连要重新读凭据， 提示就落在那儿。

明明在跑的 agent，Agents 区里看不到

什么意思。Agents 区列的是 herdr 自己那些 pane 里的 agent， 不是这台机器上所有的 agent 进程。你在 Terminal.app 里起的 claude 它是看不见的。herdr 是一个 runtime，不是进程扫描器——它靠盯自己的 pane 来识别 agent。

怎么办。用 New Agent Task 起，或者在一个 herdr pane 里跑它。 两种都行，下一次轮询就会出现。
