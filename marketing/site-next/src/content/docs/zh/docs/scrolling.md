## 一次划动做了什么

- **在普通 shell 里**——你翻的是真实的滚动历史，它保存在手机本地。连接（attach）时 Moshpit 会先从 tmux 预载这个窗格最近的历史，所以哪怕是你连上来之前打印的输出，也有得翻。
- **在全屏应用里**——划动变成滚轮事件转发给应用，让它自己滚。全程打字照常工作。

## 它怎么决定

在 tmux 上，Moshpit 会询问 tmux 这个窗格的程序有没有抓鼠标，然后据此路由。在 [herdr](/zh/docs/herdr) 上连问都不用问：滚动是协议动作，由*服务端*决定它变成鼠标报告还是历史翻页。这是 herdr 悄悄更好的地方之一。

## 输出还在滚动时阅读

窗格还在打印时上翻，本来是一场拉锯：你翻上去读，下一波输出把视图拽回底部。Moshpit 会在你上翻期间攒住新输出，等你回来的那一刻原样补放——往下滚回底部，或者直接打字，视图立刻回到实时画面，一个字节不丢。

## 为什么永远不碰 tmux copy-mode

滚动 tmux 窗格最「显然」的办法是 tmux 自己的 copy-mode——而它恰恰与 Moshpit 和 tmux 的对话方式相克。Moshpit 走的是控制模式（control mode），而 tmux 只为普通终端客户端绘制 copy-mode：控制模式客户端在 copy-mode 滚动期间*什么都收不到*。更糟的是，进入 copy-mode 是服务端状态——它会把挂在同一个窗口上的桌面终端也一起劫持进 copy-mode。所以在 SSH+tmux 上，划动永远不触碰 copy-mode；滚动历史就在手机上。（[mosh+tmux](/zh/docs/mosh) 路径不同：那里的渲染器*是*普通客户端，copy-mode 正是对的工具——见那一页。）

## 值得知道的边界

- **不用多路复用器时**，滚动历史就是应用自己在内存里为这个会话保留的那部分。断线后什么都不会留下。
- **在 SSH+tmux 上**，本地缓冲在连接时只预载窗格历史最近的一段，不是全部——tmux 服务端仍然保有完整历史。
- **在 herdr 上**，历史翻页由服务端按需完成——herdr 没有导出整个历史缓冲的 API，所以本地没有可搜索的副本。
- **在 Mosh 之上**，协议传输的是可见屏幕而非字节流，所以滚动历史属于里面跑的多路复用器，不属于 Mosh。
