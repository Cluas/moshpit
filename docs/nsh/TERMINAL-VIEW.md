给谁看：做 Moshpit 的人和替他干活的 agent。解决什么问题：iOS 的终端视图要从 SwiftTerm 分叉换到共享的 Rust 内核（`crates/term`）上。SwiftTerm 分叉的视图层是几年补丁叠出来的，Cluas 定了：不照搬它的代码，按工程上最好的分层重做；分叉 32 个视图层补丁和老 bug 账里的视图条目是**需求**，每条变成验收测试。同样的分层要给 Android 的视图用。

## 1. 分层

一句话：凡是和平台无关的终端逻辑都在 Rust（`crates/term`），能在 Mac 上不开界面测；平台视图只做画图、接系统输入、发意图。

| 层 | 在哪 | 管什么 |
| --- | --- | --- |
| 内核 `Terminal` | `crates/term/src/lib.rs` | 屏幕、历史、损伤（帧只带变了的行）、选区（字符、词、行、块、语义）、搜索、链接（OSC 8 和识别出的网址）、模式 |
| 输入编码 `input` | `crates/term/src/input.rs` | 按键（xterm、DECCKM、kitty 协议的按下/连发/松开）、鼠标、焦点、粘贴（括号粘贴和去标记） |
| 预测回显 `predict` | `crates/term/src/predict.rs` | mosh 的预测引擎，猜测叠在帧上 |
| 输入法对账 `ime` | `crates/term/src/ime.rs` | 纯函数：系统文字输入说了什么、我们已经发了什么，算出要发的字节；幻影换行、第三方键盘的编辑回报、组字删除、自动句号都是它的用例 |
| 滚动模型 `scroll` | `crates/term/src/scroll.rs` | 历史里的像素偏移、去向（本地历史、给程序的滚轮、交给宿主的行）、半行吸附、惯性（数据，默认关） |
| 点按意图 `gesture` | `crates/term/src/gesture.rs` | 一次点按是什么：关选区、开链接、点鼠标、要键盘；双击、三击、长按的选区 |
| 无障碍文字 `a11y` | `crates/term/src/a11y.rs` | 可见行的文字、光标、要播报的变化 |
| 字节通道 `pane` | `crates/term/src/pane.rs` | 解析在 pane 线程；视图自己喂的本地通道（`Pane::local`），尺寸和重置按序走在字节中间 |
| C 接口 | `crates/term/src/ffi.rs`、`include/moshpit_term.h` | 上面每一层的 `mp_term_*`，iOS 走 Swift，Android 走 JNI |
| iOS 适配层 | `Moshpit/UI/Terminal/Core/` | Metal 画帧（Metal 不可用才用 CoreGraphics）；`UITextInput` 转给 `ime`；手势只发意图；UIKit 的菜单、把手、指针；VoiceOver 元素读 `a11y` |
| 接缝 `TerminalSurface` | `Moshpit/UI/Terminal/TerminalSurface.swift` | App 代码问终端的一切：字节和夹在字节里的标记、格子和网格、光标和程序的模式、本地历史和拖动的去向、程序的鼠标、粘贴字节、行文字、快照、外观、mosh 预测。终端回话走 `TerminalSurfaceDelegate`。两个视图都实现它；`TerminalSurfaces.make` 按开关造 |
| SwiftTerm 适配层 | `Moshpit/UI/Terminal/SwiftTerm/` | `SwiftTermSurface` 包着分叉的 `TerminalView`，以及只属于 SwiftTerm 的事：读历史时扣住输出、每次喂完重设用户光标、给格子打链接标、预测写进格子、滚动和捏合手势。**App 里只有这个目录 import SwiftTerm** |
| 宿主 | `SwiftTerminalView.Coordinator` 等 | 拥有一个 `TerminalSurface`，会话级的去向：tmux/herdr 的滚动和点击、粘贴走哪条路、键盘起落的冻结、遮罩、标记到点要做的事。不知道是哪个视图在画 |

不放进 Rust 的：画图本身、系统输入法的协议（`UITextInput` 的位置和区间对象）、手势识别、菜单和把手的 UIKit 控件、VoiceOver 元素对象、键盘的系统连发计时（iPadOS 不给设置，Mac 读系统值）。这些平台各写各的，但每个只把系统事件翻成对内核的一次调用。

## 2. 数据流和线程

```
字节进：会话（Swift 传输或 Rust 内核）→ 协调器 feed → mp_term_push ──本地字节通道──▶ pane 线程解析
                                                                     │ 唤醒（最多一个在途）
画：主线程 ◀────── 一次跳转 ──────────────────────────────────────────┘
     mp_term_take_frame（pane 线程发布的帧：变了的行的拷贝，不拿锁）→ 只重编码这些行 → Metal 画整屏（GPU 便宜）
字节出：按键 / 输入法 / 粘贴 / 鼠标 → mp_term_*（编码在内核）→ 字节 → 协调器 sendInput → 会话
回复：内核的 DA/CPR 等由 pane 线程攒着，主线程取帧时一起发出（mp_term_take_replies）
```

- **铁律**：每个方向一条队列，不乱序、不丢。本地通道用的就是 `crates/stream` 的队列；尺寸变化和重连时的「丢掉半截序列」作为队列里的标记，落在它前后的字节之间。
- **主线程只做**：取帧（拷贝）、重编码变了的行、提交 Metal。解析永远不在主线程。帧的节奏：按键回显那种孤立的唤醒立刻取帧立刻画；整屏连着来时（主线程歇的还没有上一帧花的时间长）等到下一次刷新，每次刷新最多套一帧；便宜的帧（回显、提示符）随到随取（T4）；GPU 手里已有两帧就等下一次刷新，主线程从不等可画的缓冲。
- **帧由 pane 线程做**（T4）：它本来就拿着锁，每次解析完一段、以及长段解析（积压）中每 16 ms，把变了的行做成一帧放进一格的槽、叫醒视图；视图取槽里的帧不拿锁（`mp_term_take_frame`）。槽里的帧没被取走就不做新的，伤痕留在终端里，下一帧一起带上；视图取走时解析已经往前走了，就叫 pane 线程把剩下的也做出来。视图自己引起的变化（滚动、选区、换外观）当场做帧（`mp_term_frame`）：先给槽里那帧，自己的这帧放回槽里，按序。事件（标题、响铃、OSC 7、剪贴板）也由 pane 线程边解析边挪出终端，视图取的时候不拿锁。
- **锁**：内核的 `Terminal` 一把锁。pane 线程每读 64 KB 放一次锁。主线程平常取帧、取事件、取回复都不拿它；只有视图自己的操作（按键编码、滚动、选区、自己做帧）要拿，最多等一次 64 KB 的解析。
- **标记随帧走**（T3）：会话通道里的标记（切 pane 的遮罩、揭幕、读历史的扣放）由协调器推进视图的字节队列（`TerminalSurface.feed(mark:)`），解析走到它时记下，下一帧带回来（`mp_frame_mark`），视图取到这一帧、画之前交给协调器。所以揭幕一定和带着它之前那次重画的帧一起，不会揭开在还没解析完的重画上；遮罩一定不晚于带着它之后字节的第一帧。帧和它的标记在同一把锁下取。同步更新（2026）里的标记等更新结束（或超时）才走，和那些字节一样。SwiftTerm 喂的时候就解析完，标记当场交回。
- **留着等重画的尺寸**（`applyDeferredResize`）不进队列：协调器读到它就改视图的 frame，内核视图在 frame 改的当下 `mp_term_resize`（本地通道里按序），所以新尺寸落在重画字节之前，和 SwiftTerm 在 frame setter 里改尺寸一样。
- Rust 会话路径现在仍经协调器（主线程拷一次再推给内核）。让 pane 线程直接读会话的通道见 §7。

## 3. 接口（C ABI 摘要）

- 生命周期和字节：`mp_term_open_local`、`mp_term_push`、`mp_term_push_mark`（T3，ABI 6：标记夹在字节里，最高位留给内核自己）、`mp_term_resize`（按序）、`mp_term_discard_pending_input`、`mp_term_close`；`mp_term_take_replies`、`mp_term_take_events`（标题、响铃、OSC 52、OSC 7；打开的终端不拿锁）。
- 帧：`mp_term_take_frame`（T4，ABI 8：pane 线程发布的那一帧，不拿锁，没有就是 NULL）、`mp_term_frame`（视图自己的变化：先给发布了没取的那帧，自己的放回去，之后接着 `mp_term_take_frame` 取到 NULL）、`mp_frame_info`（含 `marks`）、`mp_frame_row`、`mp_frame_image`、`mp_frame_mark`；`mp_term_set_extra_rows`（像素滚动时多带视口下面一行）。`mp_term_open` 打开的终端，会话通道的标记也这样随帧走。
- 外观：`mp_term_set_palette`、`mp_term_set_cell_pixels`、`mp_term_set_bold_is_bright`、`mp_term_set_scrollback`。
- 输入编码：`mp_term_key`、`mp_term_mouse`、`mp_term_focus`、`mp_term_paste`。
- 输入法：`mp_term_ime_*`（插入、删除、设组字、结束组字、替换、设选中区间）→ 要发的字节，加上「这次变化是不是系统自己做的」；`mp_term_ime_state` 给适配层回答 `UITextInput` 的位置查询。
- 滚动：`mp_term_scroll_drag`（手指位移、去向参数）→ 动作（本地已滚、滚轮字节、交给宿主的行数）；`mp_term_scroll_end`；`mp_term_scroll_state`。
- 点按和选区：`mp_term_tap`（格子、光标附近、是否在读历史、是否有选区）→ 意图；`mp_term_select_*`、`mp_term_selection_text`、`mp_term_selection_bounds`；`mp_term_link_at`（OSC 8 优先，其次识别出的网址，再次主机确认过的路径）；`mp_term_search`（正则）。
- 路径链接（T3，ABI 7）：`mp_term_set_path_extensions`（平台能预览哪些扩展名，空串关掉）、`mp_term_path_candidates`（屏上的候选，每个一次）、`mp_term_set_path_links`（主机确认过的那一套，整套替换）。OSC 7 是事件 `MP_TERM_EVENT_DIRECTORY`。
- 查找（T3）：`mp_term_find`（按字面、默认不分大小写、可选词首词尾，返回第几个、一共几个，到头绕回）、`mp_term_search_clear`。
- 无障碍：`mp_term_a11y_line`、`mp_term_a11y_take_announcement`。
- tmux pane 的清屏（T9，ABI 10）：`mp_term_set_tmux_clears`。
- 图片的内存（T7，ABI 9）：`mp_term_images_purge`（全进程的解码缓存）、`mp_term_release_image_caches`（一个终端为共用留的图，进后台）、`mp_term_drop_unplaced_images`（再加没格子显示的 kitty 图，内存警告）；`mp_term_images_bytes`、`mp_term_kitty_image_bytes` 给调试用。

### 5.6 T4：积压时画面照常走（B279，iPad mini，iOS 18.2，2026-11-13）

**问题**（§5.5 末尾查出）：pane 线程一段解析读到的都是整块（积压）时，整段解析完才叫视图，画面停在旧的直到解析完。1.0.8 (105) 起内核视图默认开，这成了用户看得到的：SSH 从后台回来、长取屏、大文件 `cat`。

**做法**（`a1ae8303`）：帧由 pane 线程自己做。它本来就拿着锁，每段解析结束、以及长段里每 16 ms（`PUBLISH`）做一帧放进一格的槽、叫视图；视图取槽不拿锁（`mp_term_take_frame`，ABI 8）。槽没空就不做新的，伤痕留在终端里下一帧一起带；视图取走时解析已往前走，就叫 pane 线程把剩下的也做出来。视图自己的变化（滚动、选区）当场做帧，排在发布了没取的那帧后面。标记随帧：每帧带着解析走到的标记，视图拿到帧、画之前交出去。字节一条队列一个读者，不丢不乱，和以前一样。`tests/backlog.rs` 证明长积压出中间帧、只往前、一行不丢不乱（Mac release 60 万行：1.9 s 里 108 帧，间隔中位 17 ms）。

**主线程卡顿**（门 T1：最长 < 32 ms）。只做上面这一步，积压时主线程最长间隔从 16.7 ms 变成 42–55 ms（之前积压时主线程什么都不做，所以是 16.7）。加了每帧分项计时（`6d4ead89`）查出五样，按大小：

1. 一次转一帧整屏（iPad mini 的网格大，约 1.3 万格）：Debug 里编码 12–19 ms，大头是带检查的数组下标、每格一次字典查字形。改成指针、ASCII 字形查表（`d9307ec2`）：8–12 ms。

### 5.9 T9：tmux pane 的清屏跟 tmux 一致，内存警告后剩下的（B296、B297，2026-11-13）

**B296：tmux pane 里 `clear` 之后能翻回去的，和 tmux 自己留的一样**（`e720b48d`）。协调者定的：只对 tmux pane。tmux 3.6a 的 `scroll-on-clear`（默认开）在私有 tmux 上量出来的规则：`ESC [2J` 光标在哪都算；`ESC [J` 只有光标在左上角才算（tmux pane 的 terminfo 是 `tmux-256color`，`clear` 发的正是 `ESC [H ESC [J`），别处的 `ESC [J` 不算；备用屏幕上一律不算；推进历史的是屏上直到最后一个「用过的」行。我们原来的 scroll-on-clear 只认 `ESC [2J`。

- 做法：wezterm 配置里加一个开关（W23，默认关），开着时主屏幕上从左上角的 `ESC [J` 和 `ESC [2J` 一样先把屏幕推进历史；内核的 `Options::scroll_on_clear = ScrollOnClear::Tmux`，C ABI 10 `mp_term_set_tmux_clears`；App 里两个 tmux 控制器给每个 pane 的终端调 `followTmuxClears()`。裸 SSH、mosh、herdr 不变。pane 的 `scroll-on-clear` 选项没去读：读它要每个 pane 一次 `show-options` 来回，而它几乎没人改；就按默认开。
- 证明：`crates/term/tests/tmux_clear.rs` 把同一串字节同时喂给一个私有 tmux 3.6a（自己的 socket、`-f /dev/null`，pane 里的程序原样写出这些字节，和 `-CC` 客户端收到的一样）和内核，逐行比历史（`capture-pane -p -S -<history_size> -E -1`）和屏幕：`clear`、不在左上角的 `ESC [J`、光标在中间的 `ESC [2J`、备用屏幕上的清屏、连清两次、原地重画的 TUI、每帧都清屏的 TUI（`watch` 那种：tmux 每帧都留进历史，我们一样）、Claude 那样的行内重画（同步更新里上移 8 行、逐行 `ESC [2K` 重写）、Claude 那样的 `ESC [2J ESC [3J` 整屏重画：全部逐行相同；不开开关时三个不同。

## 6. T3 的决定（2026-11-12）

- **接缝是一个协议加一个委托**（`TerminalSurface` / `TerminalSurfaceDelegate`），不是按调用方拆成几个小协议。调用方要的东西大多一起要（协调器一个就用了七成），拆开只多出类型、不少依赖；Android 的视图将来对着同一张清单实现。视图特有的东西（SwiftTerm 的扣住输出、打链接标、往格子里写预测；内核的帧、Metal）留在各自的适配层里。
- **两条会话路径的 tmux pane 都跟开关走**（Rust 路径是主线，必须；Swift 路径的 `TmuxSessionController` 原以为改起来贵、打算留在 SwiftTerm，查下来不贵就一起换了）。前提是「喂完不等于已经解析」：查了 Swift 控制器里所有喂字节、挂遮罩、揭幕、应用延迟尺寸的地方（7 处喂、5 处遮罩、2 处延迟尺寸、1 处揭幕），只有 capture 喂完同一轮揭幕这 1 处依赖同步解析，改成 `Coordinator.revealWhenShown()`（协调器自己的标记，跟在字节后面，到点才揭幕）。同一个毛病在 Swift 会话的 SSH + herdr 上也有（整帧喂完马上揭幕，内核视图上会揭在没画完的帧上，T2 留下的），一并改了。控制器在造出来时读一次开关（一个 attach 里的 pane 视图一致）。
- **标记随帧走，不随推送走**，遮罩也一样（不提前）：提前做遮罩看着更保险，但 A→B→A 快切时，A 上一轮还在队列里的揭幕会揭开 A 这一轮刚提前挂上的遮罩，露出半截重画。全按队列顺序，每个标记只在它前面的字节上屏时生效，就没有这种交错。代价是遮罩比 SwiftTerm 晚一次 pane 线程到主线程的跳转（< 1 帧）。
- **留着等重画的尺寸读到就做**（不进队列）：它要求「新尺寸在重画字节之前」，协调器读到标记时重画字节还没推，当场改 frame 就满足；内核视图在 frame setter 里立刻把 resize 放进字节队列，和 SwiftTerm 一致。
- **路径扫描放进 `crates/term`**（照 App 的 `TerminalPathScanner` 逐条移植，一格一个字），能预览哪些扩展名由平台给（iOS 是 QuickLook 那一套）：Android 以后直接用。主机确认、缓存、探测仍在 App 的 `RemotePathLinks`（走会话的连接）。确认过的路径不写进格子（SwiftTerm 那样打标会改动服务器以为的屏幕），而是内核记一张「token → 链接」表，取帧时只在变了的行上找、点按时现找；表变了整屏重画一次。每次扫描交出屏上全部确认过的，内核整套替换，所以工作目录变了旧的相对路径自然掉出去。两个扫描器（Swift、Rust）在真机上逐行对照，防止各改各的。
- **查找用系统的查找条**（`UIFindInteraction` + 自己的 `UIFindSession`），不自己画：原生质感、键盘快捷键和本地化都是系统的；按字面而不是正则（正则留给 `mp_term_search`）。从最新的匹配开始（终端里刚看过的在底部）。只标当前那一个匹配，不把全部匹配都上色（要全部上色得每帧在变了的行上跑一遍查找，先不做）。手机上没有键盘时从长按菜单的「查找」进；终端顶栏上不另加入口（产品决定，留给 Cluas）。
- **测试里碰 SwiftTerm 的**走 `Tests/MoshpitTests/Support/SwiftTermAccess.swift`（`coordinator.terminalView`、`controller.terminalView(for:)` 等测试专用的接法），App 代码里没有这些。

### T4 的决定（2026-11-13）

- **帧由 pane 线程按时间做，视图不多拉**（B279）：协调者给的两个方向里选了这个。视图多拉（T3 分支里的「每 8 ms 叫一次视图」）每次都要拿锁、和解析抢；pane 线程反正拿着锁，顺手做帧最便宜，主线程平常一次锁都不用拿。槽只放一帧：视图来不及取，中间的状态就合进下一帧（字节一个不丢，只是屏幕少画几个中间样子）。
- **按代价节流，不按时间**：主线程歇的还没有上一帧花的时间长，下一帧就等显示链接，一次刷新一帧；便宜的帧随到随取。按时间（离上一帧不到一次刷新就等）会把紧跟在别的帧后面的回显拖一次刷新（tmux 上每次都是）。只算唤醒和显示链接取的帧，视图自己做的不算。
- **W19 留下**：ASCII 行按字节切格子，不经字素分割（帧的建造少一半以上，做帧的代价因此和之前持平）。中日韩行照旧分割。
- **ABI 8**（`mp_term_take_frame`），T7 升到 9（图片的内存）。没合并的 `nsh-term/t3-direct-reading` 用的是 8，以后要合它得升到 9 之后。
